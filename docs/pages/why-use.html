Why Use json-renderers-guard?

The story of evolving from monolithic specification builders into a resilient, drift-free decoupled architecture.

1. The Monolithic Problem

In early declarative UI architectures, component builders (such as json-renderers-build-table) were monolithic. A single module performed multiple contradictory jobs:

  • Validating input JSON shapes and data types.
  • Iterating over column definitions and computing cell specifications.
  • Generating DOM AST objects.
  • Checking DOM mount target containers and injecting elements into the document.

When validation rules were bundled directly inside builder or renderer code, reusing those rules across tests, build steps, or backend services required copying validation code or importing heavy DOM-dependent modules into environments that had no DOM.

The Danger of Duplication: When validation functions are duplicated across repositories, they inevitably drift out of sync. One package might enforce that columnName is required, while another might silently ignore missing columns, causing unexpected runtime crashes deep inside DOM mutation loops.

2. The Architecture Solution: GUARD as a Boundary Perimeter

json-renderers-guard introduces a clean architectural perimeter. Instead of validation being scattered across downstream builders, GUARD acts as a single, centralized contract authority:

Layer Package Core Responsibility Has DOM Access?
Validation Guard json-renderers-guard Validates input contracts, schema rules, and field requirements. ❌ No (Pure Data)
Specification Builder json-renderers-build-table Transforms validated configs into declarative AST tree specifications. ❌ No (Pure Data)
Renderer Orchestrator json-renderers Manages container lifecycle, replace/append logic, and CSS classes. ✅ Yes (Browser/JSDOM)
DOM Engine json-to-tag Instantiates real native DOM elements and attributes. ✅ Yes (Browser)

3. Why Separate Spec Validation from Mount Validation?

Modern web applications often generate specifications ahead of time (e.g. in Node.js server-side rendering, CLI report generation, or Web Worker background threads) where no DOM element exists yet.

GUARD solves this through its Dual-Phase Architecture:

  • guardSpec(): Validates only the specification keys (type, data, columns, showLog). It never demands a targetHtmlId. This allows headless pipelines to validate data contracts cleanly.
  • guardMount(): Validates mounting concerns (targetHtmlId, appendPosition, classToApply). This ensures a valid DOM container identifier before mounting begins.
  • guardFunc(): Composes both guards together to validate complete end-to-end client rendering requests in one pass.

4. Key Benefits at a Glance

  • Fail-Fast Boundary: Errors are thrown immediately at the entry point with descriptive diagnostics, rather than failing silently or causing cryptic DOM errors later.
  • Zero Runtime Dependencies: Pure ES Module with no external libraries, keeping package weight negligible.
  • Tooling & NPX Support: Test and validate JSON files in CI/CD without writing custom validation code.
